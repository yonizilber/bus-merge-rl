## מצב

push. דוח הבדיקות (באתר ה-HTML) מפרט כל מקרה בדיקה עם התוצאה שלו, מאותה הרצה אמיתית.

xfail קשיח[^strict_xfail] הוא בדיקה למגבלה ידועה: היא חייבת להיכשל על ההנחה שלה, והיא הופכת לאדומה ביום שההתנהגות משתנה, כך
שאי אפשר להסתיר מגבלה וגם אי אפשר לתקן אותה בלי שמישהו ישים לב.

**עבודה עתידית.**
- לכתוב מחדש או למחוק את 9 הבדיקות הישנות.
- לתקן את הבדיקה שתמיד מדלגת: `test_follower_telemetry.py` מריצה 200 צעדים, שנגמרים לפני שהאוטובוס משתלב, ולכן אף פעם אין לה
  מה לבדוק.
- להוסיף בדיקות למגבלות שעדיין אין להן: O11 (האוטובוס מסתובב סביב מרכזו), O15 (קריטריון ההשתלבות לאוטובוס מוטה), O16 (היגוי
  הכניסה למפרץ במהירות).

## מתי הבדיקות רצות

| מתי | מה רץ | חוסם? |
|---|---|---|
| בכל push ובכל pull request (GitHub Actions, ‏`ci.yml`) | `ruff` וכל החבילה פרט לשערים הסטטיסטיים, כשתי דקות | **כן**: pull request מתמזג ל-`main` רק כשזה עובר |
| משימה מתוזמנת, כל יום ב-02:00 UTC, ולפי דרישה (`nightly.yml`, ‏`cron` ו-`workflow_dispatch`) | 5 השערים הסטטיסטיים: מוח ברירת המחדל על 400 הרצות ב-seeds שלא נראו | לא; הם שומרים מפני סחיפה איטית, ורצים לפני כל שחרור |
| לפני שחרור | שער הקבלה ואימות על 1,000 seeds לכל מספר מתפרסם | כן, לפי הכלל |

**כלל הפיתוח.** הענף `main` מוגן: העבודה נעשית בענף צד, מגיעה ל-`main` רק דרך pull request, ו-pull request מתמזג רק כשה-CI ירוק.
מה חוסם מיזוג:
- כל בדיקה שנכשלת או שגיאת lint;
- xfail קשיח שמתחיל לעבור (פירושו שמגבלה השתנתה: מעדכנים את הבדיקה ואת התיעוד);
- כל בדיקה חדשה שנכשלת בלי סיבה מתועדת.

מה מאושר: 22 ה-xfail הקשיחים, כל אחד מקושר לרשומה ב-`docs/reference/BUGS.md`, ו-6 הדילוגים שלמעלה.

קובצי ה-workflow נמצאים ב-`.github/workflows/`. הגנת הענף (ה-"required status check") היא הגדרה של המאגר, שמופעלת כשהמאגר
מתפרסם.

## קבוצות ה-seeds

ה-seeds האקראיים מחולקים לטווחים נפרדים, כך שאף מספר לא נמדד על נתונים שכוונן עליהם: 1000-1099 לבחירה בין מוחות מועמדים,
2000-2999 למספרים המתפרסמים, 3000-3249 לשערים המתוזמנים.

## הרצת הבדיקות

```bash
pip install -e ".[dev]"
ruff check . && pytest -q               # what CI runs on every push
pytest --nightly -m nightly             # the scheduled statistical gates
python scripts/build_test_report.py     # run everything and write the test report
```

[^strict_xfail]: **בדיקת xfail קשיחה (strict xfail).** בדיקה על מגבלה ידועה: היא שומרת על ההנחה הכנה שלה, חייבת להיכשל עליה, והופכת לאדומה ביום שההתנהגות משתנה. מחיקת הבדיקה או הרפיית הסף שלה היתה מסתירה את המגבלה. עם xfail קשיח היא נשארת בחבילה, ליד הקוד, ולא יכולה להתחיל לעבור בשקט או להישבר מסיבה אחרת. [עוד](GLOSSARY.md#strict_xfail)
[^invariants]: **בדיקות פיזיקה (invariants).** בדיקות שרצות על כל הרצה מדומה ומחפשות רגעים שאי אפשר שיקרו במציאות. הרצה לא נשפטת רק לפי התוצאה שלה. `busmerge/invariants.py` עובר על כל יומן הפריימים ומדווח על כל רגע בלתי אפשרי. מכוניות שחוצות את קו האמצע או את המדרכה מדווחות אבל לא נכשלות (בעיקר בגלל חריגה של חוק ההיגוי שלהן כשהן מפנות דרך לאוטובוס, מגבלה O21). [עוד](GLOSSARY.md#invariants)
[^property_test]: **בדיקה מבוססת-תכונות (property-based test).** בדיקה שמצהירה על כלל ("אף פעם לא בולם חזק מ-9 מ'/שנ'²") וספרייה מנסה אלפי מקרים שנוצרים אוטומטית. הספרייה `hypothesis` מייצרת את המקרים, וכשהיא מוצאת דוגמה נגדית היא מקטינה אותה למקרה הקטן ביותר. היא מצאה את החדירה של חוק המהירות הבטוחה אל תוך המרווח המינימלי (מגבלה O19). [עוד](GLOSSARY.md#property_test)
[^pure_pursuit]: **היגוי Pure pursuit.** שיטת היגוי: מכוונים אל הנקודה שעל קו היעד במרחק look-ahead קדימה, במערכת הצירים של הרכב עצמו, ומנווטים לאורך הקשת שמגיעה אליה. מכיוון שהנוסחה כוללת את כיוון הרכב, הרכב מסובב את ההגה בחזרה כשהוא מתקרב לקו, ומגיע מקביל אליו במקום לחצות אותו. זה הבקר שהחליף את הבקר שחרג מכל יעד. [עוד](GLOSSARY.md#pure_pursuit)
[^rollback]: **כלל ה-rollback (rollback rule).** באימון: אחרי כמה הערכות בלי שיפור, חוזרים ל-checkpoint הטוב ביותר עד כה. לכוונון עדין שמתחיל בלי הערכה מוצלחת אחת אין "הטוב ביותר" פרט למשקולות ההתחלה, ולכן הכלל זרק כל 30 epochs של למידה. עכשיו זה דגל (`--rollback-patience`), והוא משחזר רק checkpoint שהוערך עם הצלחה אחת לפחות. [עוד](GLOSSARY.md#rollback)
